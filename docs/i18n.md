# Internationalization (i18n)

## Strategy

- Library: **`next-intl`** (App Router–native, supports RSC, has proper plurals and dates).
- URL structure: `/en/...` and `/ko/...` (prefix-based — best for SEO and shareable links).
- Default locale: **`en`** (primary audience is international).
- Supported: `en`, `ko`.

## Locale detection

1. On first visit, middleware reads `Accept-Language` header.
2. If best match is `ko`, redirect to `/ko/...`. Otherwise, `/en/...`.
3. User's explicit choice stored in cookie `NEXT_LOCALE` — overrides `Accept-Language`.
4. Locale toggle (header + settings) sets the cookie and reroutes.

## File layout

```
apps/web/
├── i18n.ts                            # next-intl config
├── middleware.ts                       # locale detection
├── messages/
│   ├── en.json                         # English messages
│   └── ko.json                         # Korean messages
└── app/
    ├── [locale]/
    │   ├── layout.tsx                  # wraps with NextIntlClientProvider
    │   ├── page.tsx                    # home (View Teams)
    │   ├── teams/...
    │   ├── search/...
    │   └── ...
    └── api/...                         # API routes — locale-independent
```

API routes live OUTSIDE `[locale]` since they return JSON, not localized HTML.

## Message namespace convention

Top-level keys correspond to screens, plus shared `common` and `nav`:

```json
{
  "common": { "save": "...", "cancel": "...", "delete": "...", ... },
  "nav": { "viewTeams": "...", "createTeam": "...", "quickSearch": "..." },
  "home": { "popularTeams": "...", "sortLikes": "...", "empty": "...", ... },
  "teamDetail": { "edit": "...", "delete": "...", "physicalBulk": "...", ... },
  "search": { "placeholder": "...", "noMatch": "...", "recentSearches": "...", ... },
  "create": { ... },
  "comments": { ... },
  "errors": { "required": "...", "tooLong": "...", ... }
}
```

## User content vs. system content

| Content type | Translation behavior | Source |
|---|---|---|
| UI labels, buttons, placeholders | Translated via messages | `messages/*.json` |
| Pokémon names | Translated via DB column | `pokemons.name_en` / `pokemons.name_ko` |
| Move / ability / item / nature names | Translated via DB column | Same pattern |
| Team name / description | **Not translated** — stored as-is | User input |
| Comment body / nickname | **Not translated** — stored as-is | User input |

## Bilingual search

Quick Search and the Pokémon picker must accept queries in either language and return results with display name in the current UI locale.

### Query strategy

```sql
SELECT id, name_en, name_ko, ... FROM pokemons
WHERE name_en ILIKE :q || '%'
   OR name_ko ILIKE :q || '%'
ORDER BY
  CASE WHEN name_en ILIKE :q || '%' THEN 1 ELSE 2 END,
  length(coalesce(name_en, name_ko)) ASC
LIMIT 10;
```

Korean `ILIKE` works but hangul-jamo decomposition does NOT. Users typing "리자" will match "리자몽" directly; partial jamo input (e.g. "ㄹㅣㅈ") is NOT supported in v1.

For the primary search endpoint (not autocomplete), use PostgreSQL `pg_trgm` extension with GIN indexes on both `name_en` and `name_ko` for fast substring matching.

### Display name resolution

After finding a Pokémon row, pick the display name based on current locale:

```ts
function displayName(row: { name_en: string; name_ko: string }, locale: Locale) {
  return locale === 'ko' ? row.name_ko : row.name_en;
}
```

Autocomplete items show the primary name + secondary language in muted text:

```
리자몽 (Charizard)   ← if locale is ko
Charizard (리자몽)   ← if locale is en
```

## Pluralization

Use ICU message syntax via `next-intl`:

```json
{
  "viewCount": "{count, plural, =0 {No views} one {# view} other {# views}}"
}
```

Korean plurals collapse to `other` (no inflection), so Korean message:

```json
{ "viewCount": "조회 {count}" }
```

## Date / relative time

Use `Intl.RelativeTimeFormat(locale)` directly. Wrap in a small helper `formatRelative(date, locale)` in `apps/web/lib/date.ts`.

## Font

Use **Pretendard** as primary — covers Latin and Korean both with consistent metrics. Fallback to `system-ui`.

```css
font-family: 'Pretendard Variable', Pretendard, -apple-system, system-ui, sans-serif;
```

Load via CDN (jsdelivr) or self-host. Self-host preferred for offline PWA.

## Line-height and layout considerations

- Korean glyphs are denser — give `line-height: 1.6` for body text.
- Buttons with Korean labels often need slightly more vertical padding than English equivalents. Check both locales in Playwright tests.
- Long English words (e.g. "Password confirmation") may cause layout issues in narrow mobile; prefer short labels like "Confirm password" when possible.

## Adding a third locale later

Adding `ja` or `zh` requires:
1. Create `messages/{locale}.json`.
2. Add the locale code to `i18n.ts` supported list.
3. Add `name_ja` / `name_zh` columns to master data tables (schema migration + crawler update).
4. Update search endpoint to include new columns.

## Testing i18n

- Playwright: run every smoke test twice, once per locale (parametrized).
- Check visual regressions in both locales (Korean strings often break layouts).
- Unit test the locale detection middleware with `Accept-Language` variations.
